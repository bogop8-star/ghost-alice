# PRD: Ghost-ALICE OS & Autopilot 실사용 개선 프로젝트

- 원본 기획서: [project-docs/project-plan.md](https://github.com/bogop8-star/ghost-alice/blob/main/project-docs/project-plan.md) (bogop8-star/ghost-alice `main`, commit `f1e8377`, 2026-11-12, 작성자 @우디)
- 문서 상태: 초안. 기획서에 없는 값은 지어내지 않고 [열린 질문](#9-열린-질문)에 남겼습니다.

## 1. 배경

Ghost-ALICE OS(본체)와 Ghost-ALICE Autopilot(공식 애드온)은 Agent의 의도, 작업 범위, 승인, 완료 조건을 관리하는 프레임워크입니다. 하지만 설치·호환성 오류와 훅 동작 문제 때문에 일반 사용자가 바로 쓰기 어렵습니다. 팀도 설치 과정에서만 실제 문제 4건을 만났습니다.

이 프로젝트는 새 Agent나 데모를 만들지 않습니다. 이미 있는 프레임워크를 일반 사용자가 쓸 수 있는 수준으로 끌어올리는 것이 목적입니다. 에이드올 과제 정의서(v4)의 "Ghost-ALICE와 Autopilot의 문제를 발견한 경우" 항목과 우선 조사 트랙이 주 과제입니다.

- 대상 저장소: [AidALL/ghost-alice](https://github.com/AidALL/ghost-alice)(본체), [AidALL/ghost-alice-autopilot](https://github.com/AidALL/ghost-alice-autopilot)(공식 애드온)
- 팀 저장소: [bogop8-star/ghost-alice](https://github.com/bogop8-star/ghost-alice)(공개 fork)

## 2. 문제 정의

핵심 질문은 다음과 같습니다.

> Ghost-ALICE가 설치된 환경에서 Agent 답변이 부족하거나 틀릴 때, 어떤 경우에 공통적으로 발생하고 어떻게 고칠 수 있는가?

아래 유형은 출발 가설입니다. A를 뺀 나머지는 모두 재현으로 확인해야 합니다.

| 유형 | 사용자가 보는 증상 | 의심 원인 | 근거 수준 |
| --- | --- | --- | --- |
| A. 거버넌스가 조용히 꺼짐 | 의도·범위 관리가 적용되지 않은 답변 | 훅이 거부되어도 사용자에게 보이지 않음 | 확인됨(Windows 경로 표기 차이로 session-intent·Autopilot 훅 거부) |
| B. 이전 의도 재사용 | 바뀐 요청에 예전 목표로 답함 | session-intent 원장이 갱신되지 않거나 잘못 비교됨 | 미확인 |
| C. 완료 판정 오류 | 검증 없이 완료라고 하거나, 정상 답변이 막힘 | Stop 훅의 완료 검사 규칙 | 일부 단서(Windows에서 Stop 훅 테스트 다수 실패) |
| D. 안내 메시지 과다 | 답변이 거버넌스 안내로 채워져 본론이 부족 | 사용자 시스템 메시지 노출 수준(visibility) | 미확인(트랙 ①) |
| E. 반복 검증 루프 | 같은 확인을 반복하며 시간·토큰 소모 | 원장 비교·해시 검증 반복 | 미확인(트랙 ③) |

유형 A에서는 훅이 거부되면 Agent가 거버넌스 없이 답합니다. 사용자는 doctor를 실행해야만 그 사실을 알 수 있습니다.

## 3. 목표

1. 답변 품질을 떨어뜨리는 문제를 유형(A~E)별로 묶습니다.
2. 깨끗한 환경에서 재현되는 문제만 GitHub 이슈로 남깁니다. 많이 찾기보다 확실하게 재현되는 것을 우선합니다.
3. 후반부에 핵심 이슈의 수정 코드, 회귀 테스트, AidALL PR을 냅니다.

### 조사 트랙

- 주 트랙: ① 사용자 시스템 메시지 노출 수준(난이도 중상). 답변 부족·오류 문제와 가장 직접 닿아 있습니다.
- 보조 트랙: ③ 반복 검증 루프(난이도 최상). 유형 E가 재현될 때만 착수합니다.

## 4. 범위

| 범위 안 | 범위 밖 |
| --- | --- |
| 본체와 Autopilot을 함께 설치해 실제 개발 작업에 사용 | 새 Agent나 데모 앱 개발 |
| 답변이 부족하거나 틀린 사례를 기록하고 유형(A~E)으로 분류 | 모델 자체의 지식 오류 분석 |
| 깨끗한 환경에서 재현되는 문제만 GitHub 이슈로 등록 | 재현되지 않는 추측성 이슈 등록 |
| 후반부에 수정 코드, 회귀 테스트, PR 작성 | 설치된 skill·Hook 파일 직접 수정 |

## 5. 사용자와 이해관계자

| 팀원 | 같은 양식으로 사례를 기록하고 OS별로 재현할 수 있는 절차 |

## 6. 요구사항

### 6.1 작업 절차

모든 사례는 다섯 단계를 거칩니다. 재현 단계를 통과한 사례만 이슈가 됩니다.

| ID | 단계 | 요구사항 |
| --- | --- | --- |
| R1 | 설치 | 기준 commit에서 본체와 Autopilot을 함께 설치하고 `install.cmd --doctor` 결과를 저장합니다. |
| R2 | 관찰 | 팀원 각자의 실제 개발 작업에 사용하고, 답변이 부족하거나 틀린 순간을 관찰 기록 양식(6.2)으로 남깁니다. |
| R3 | 분류 | 사례를 유형 A~E로 묶고, 같은 유형이 반복되는 조건(운영체제, 플랫폼, 작업 종류)을 찾습니다. |
| R4 | 재현 | 새 사용자 계정이나 깨끗한 환경에서 같은 절차로 다시 발생시킵니다. 두 명 이상이 확인해야 통과합니다. |
| R5 | 이슈 등록 | 환경, 재현 절차, 기대 동작, 실제 동작, 비식별 증거를 담아 팀 fork에 먼저 등록하고, 묶어서 AidALL에 제출합니다. |
| R6 | 모델·프레임워크 구분 | 같은 작업을 Ghost-ALICE 없이도 실행해 비교하고, 차이가 나는 것만 다룹니다. |

### 6.2 관찰 기록 양식

한 사례당 한 줄씩 추가합니다. 환경은 필수 항목입니다.

| 날짜 | 기록자 | 환경(OS·플랫폼) | 질문·작업 | 기대한 답변 | 실제 답변 | 유형 | 재현 여부 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| (예시) 11-11 | 우디 | Windows 11 · Claude Code | 설치 후 doctor 점검 | overall: ok | session-intent 훅 거부, overall: error | A | 재현됨 |

### 6.3 증거와 개인정보

- 증거로는 doctor 출력, 훅 거부 메시지, 세션 로그 일부를 씁니다.
- 첨부 전에 경로의 사용자 이름과 토큰을 지웁니다.
- 이슈에는 토큰, 이메일, 사용자 이름이 들어간 경로, 개인 프로젝트 내용을 넣지 않습니다.

### 6.4 수정과 PR(후반부)

- 수정은 fork 브랜치에서 하고 설치기로 다시 설치합니다. 설치된 skill·Hook 파일은 직접 고치지 않습니다.
- 수정마다 수정 전에 실패하고 수정 후에 통과하는 회귀 테스트를 붙입니다.
- 기존 테스트에서 새로 실패하는 테스트가 0건이어야 합니다.

## 7. 산출물과 성공 기준

제출물의 중심은 GitHub 이슈와 코드입니다. 보고서는 이슈를 묶어 설명하는 보조 자료입니다.

| 산출물 | 성공 기준 |
| --- | --- |
| 재현 가능한 GitHub 이슈 | 3건 이상, 각 이슈에 재현 절차와 비식별 증거 포함 |
| 답변 품질 문제 유형 분석 | 유형별 발생 조건과 개선 방향을 한 표로 정리 |
| 관찰 기록 표 | 팀원 전원의 실사용 사례 포함 |
| 수정 코드와 회귀 테스트(후반부) | 수정 전 실패·수정 후 통과 테스트, 기존 테스트 새 실패 0건 |
| AidALL PR(후반부) | 핵심 이슈 기준 1건 이상 제출 |
| Autopilot 실사용 기록 | 승인된 실행 1건 이상에서 작업 종료와 재개 확인 |

이슈 3건은 제안값입니다. 재현되지 않는 것을 채워 넣어 숫자를 맞추지 않습니다.

## 8. 일정

실제 날짜는 해커톤 일정이 정해지면 채웁니다.

| 단계 | 기간 | 할 일 | 완료 기준 |
| --- | --- | --- | --- |
| 전반부 1 | 1주차 초 | 기준 commit 설치, 팀원별 환경 기록 | 팀원 전원 doctor 결과 저장 |
| 전반부 2 | 1주차 | 실사용과 관찰 기록, 유형 분류 | 관찰 사례 표 작성 |
| 전반부 3 | 1주차 말 | 깨끗한 환경 재현, 이슈 등록 | 재현된 이슈만 fork에 등록 |
| 후반부 | 2주차 | 수정 코드, 회귀 테스트, PR | 수정 전후 테스트 비교, AidALL에 PR 제출 |

## 9. 열린 질문

- 해커톤 실제 날짜는 아직 정해지지 않았습니다.
- 기준 commit은 리스크 대응상 Core `v0.5.1` 태그로 제안되어 있습니다. 최신 Core(main)를 쓸지 최종 결정이 필요합니다.
- 주 트랙 ①은 제안 상태입니다. 팀 확정이 필요합니다.
- 이슈 수 목표 3건은 제안값입니다.
- Codex 환경 설치, macOS·Linux 재현, Autopilot 승인 실행 실사용은 아직 하지 않았습니다.

## 10. 규칙과 리스크

### 규칙

- PPT·보고서·목업만 제출하지 않고, 반드시 이슈와 코드를 함께 냅니다.
- 재현되지 않은 추측은 이슈로 등록하지 않고 관찰 기록에만 남깁니다.
- 본체와 Autopilot을 항상 함께 설치해 사용합니다.
- 이슈에 민감 정보를 넣지 않습니다(6.3).
- 설치된 skill·Hook 파일은 직접 고치지 않습니다(6.4).

### 리스크

| 리스크 | 대응 |
| --- | --- |
| Autopilot이 최신 Core(main)에 설치되지 않음 | 기준 commit을 Core `v0.5.1` 태그로 두고, 이 문제를 첫 핵심 이슈로 등록 |
| 팀원마다 OS가 달라 재현 결과가 갈림 | 환경을 기록 양식에 필수로 적고, OS별로 따로 재현 |
| 답변 품질 문제가 모델 탓인지 프레임워크 탓인지 구분하기 어려움 | 같은 작업을 Ghost-ALICE 없이도 실행해 비교(R6) |
| 트랙 ③ 난이도(최상) | 유형 E가 재현될 때만 보조 트랙으로 착수 |

| 항목 | 유형 | 상태 |
