## 배경: 왜 사람 입력인지 확인하나

- UserPromptSubmit 훅에는 사람이 친 말 말고도 서브에이전트 완료 보고, 백그라운드 작업 알림, Autopilot이 넘기는 다음 작업 지시문이 똑같이 입력으로 들어온다.
- 이것을 사람 입력과 같게 취급하면 웹 페이지·파일·도구 결과·서브에이전트 보고 안의 문장(예: "두 작업을 승인한다")이 사용자 승인으로 장부에 기록될 수 있다. 이를 간접 프롬프트 인젝션(indirect prompt injection)이라 한다.
- 그래서 Core는 대화 기록에서 그 입력이 사람이 친 줄(`origin: human`)인지 확인한 뒤에야 "이번 요청"으로 확정하고(출처 확인, provenance check), 확인하지 못한 입력은 권한이 없는 것으로 닫아 둔다(기본 거부, fail-closed). 경로 등록과 완료 기록도 확정된 사람 입력에 묶인다.
- 이번 문제는 이 확인이 사람 입력을 놓친 경우다. 놓친 입력을 넘기는 처리가 없어서 뒤 입력이 전부 멈췄다(헤드 오브 라인 블로킹, head-of-line blocking).

## 원인 (코드)

- `native_transcript.py` `resolve_staged_input`: 받아 둔 입력의 글자 수와 지문이 같은 `user`/`attachment` 줄을 경계 이후에서 찾아야 확정됨. 1번 입력과 같은 사람 입력 줄은 없으므로 항상 `None`.
- `session_intent_ledger.py` `reconcile_native_inputs`: 맨 앞 입력부터 차례로 확정하고, 맨 앞이 `None` 이면 `break`. 건너뛰거나 시간이 지나면 버리는 처리가 없음.
- 결과: 1번이 영원히 맨 앞에 남고, 찾을 수 있는 2번과 그 뒤 입력 모두가 확정되지 않음. 확정된 입력이 없으면 경로 등록(`route-binding`)과 완료 기록이 거부됨.

## 해결책 (제안, 미적용)

- 당장: 새 대화창을 연다. 막힌 세션은 같은 창 안에서 풀리지 않음.
- Core: 맨 앞 입력을 찾지 못해도 뒤 입력이 대화 기록에서 확인되면, 맨 앞 입력을 "찾지 못함" 이벤트로 남기고 빼낸 뒤 계속 진행한다.
- 또는: 합쳐진 사람 입력 줄 안에 받아 둔 입력 문장이 줄 단위로 들어 있으면 같은 입력으로 인정한다.
