# Ghost-ALICE 성능 측정: 비용·시간 대비 효과 실측과 개선안 비교

Nov 24, 2026 · kyu (같은 날 갱신: 4절 6번 Autopilot 원인, 3-5절 JY 방식 비교와 함정 케이스, 6절 팀 결정과 PR #15 합침)

- 기준 버전: `test-baseline-2026-11-16` (Core `c6019ac`, Autopilot `v0.5.1` `2075768`). 개선 시험은 이 Core 위에 만든 개인 시험 브랜치(아래 6절)로 했고, 팀 저장소의 Core는 바꾸지 않았습니다.
- 확인 환경: Windows 11 Pro (W1 kyu), PowerShell 7.7 / Git Bash, Python 3.14, Claude Code 데스크톱 앱과 `claude -p` 자동 실행, 모델 Opus 5.5. 관측: Langfuse(로컬 relay) + Claude Code 대화 기록
- 관련 링크: 증거 자료 [evidence/2026-11-24/](evidence/2026-11-24/) (케이스, 실행 도구, 집계 표, Core 변경 패치)

## 0. 처음 읽는 분을 위한 용어

| 용어 | 뜻 |
| --- | --- |
| 관리 호출 | 실제 일(파일 읽기·쓰기)이 아니라 Ghost-ALICE 규칙을 지키려고 하는 도구 호출. 예: 원장 읽기, 응답 경로 등록, 응답 검토 기록 |
| 응답 경로(route) 등록 | "이번 입력은 무슨 일이고 답의 목적은 실행(execution)인지 설명(explanation)인지"를 Core 원장에 적는 일 |
| 응답 검토 | 답에 들어 있는 주장마다 근거와 맞는지, 답 전체가 요청을 지켰는지를 판정해 Core에 기록하는 일. 목적이 explanation일 때만 요구됨 |
| Stop 차단 | 답을 끝내려 할 때 Stop 훅이 규칙 위반을 찾아 답을 막고 고치게 하는 것. 한 턴에 1번만 막고, 그 뒤에는 알림만 남기고 통과시킴 |
| 근거 케이스 | 파일을 읽고 사실을 알려 주는, 근거 검토가 필요한 케이스(K2·K3·K4·K6) |

## 1. 목표

팀이 정리한 단점 중 "Ghost-ALICE와 Autopilot이 쓰는 시간과 비용에 비해 효과가 없다"를 **추정이 아닌 실제 금액**으로 확인합니다. 그리고 비용을 줄이는 개선이 **검증을 약하게 만들지 않는지**까지 같은 방식으로 재서, "검증은 그대로 두고 비용만 줄일 수 있다"를 보이는 것이 목표입니다.

## 2. 한 일

순서대로 적습니다.

1. **Langfuse 연결과 사용법 정리.** 로컬 relay가 대화 기록 파일을 읽어 Langfuse에 보내는 구조입니다. relay는 파일마다 읽은 위치를 저장하므로, 꺼져 있던 동안의 기록도 다시 켜면 이어서 올라갑니다. 단, PC를 재부팅하면 relay를 다시 켜야 합니다.
2. **실제 작업 세션 1개 분석.** Windows 검증 작업을 한 세션(11/18~19, $58.24, 모델 호출 576번)을 턴 단위로 나눴습니다. 도구 호출을 관리·화면·실제 작업으로 분류하고, 관리 호출의 직접 비용과 이월 비용(문맥에 남아 이후 호출마다 다시 읽히는 비용)을 금액으로 계산했습니다.
3. **Autopilot만 따로 계산.** Autopilot 훅이 더한 대기 시간과 문맥을 따로 쟀습니다.
4. **Stop 차단 12번을 하나씩 판정.** 차단이 실제로 답을 고치게 했는지, 형식만 고치게 했는지를 나눴습니다.
5. **개선 항목별 절감 추정.** 겹치지 않는 비용 묶음으로 나눠 개선 1~4의 절감액을 추정했습니다.
6. **추정을 실측으로 바꾸는 시험 설계.** 케이스 6개를 만들었고, 정답은 자동으로 판정합니다. 실제 설치본과 분리된 시험용 설치 폴더를 조건마다 만들었습니다.
7. **조건마다 18회씩 자동 실행.** 케이스 6개 × 3회입니다. 순서는 케이스와 조건을 섞어 돌렸습니다. 금액은 Claude Code가 실행마다 보고한 `total_cost_usd` 입니다.
8. **개선 버전을 네 번 고쳐 가며 다시 측정.** 각 버전에서 나온 문제를 보고 다음 버전을 만들었습니다(3절 표의 IMP → IMP2 → IMP3 → IMP3b).
9. **안전 확인.** 매 단계 전후로 실제 설치본의 파일 지문(921개)을 비교해 바뀌지 않았음을 확인했습니다. 시험용 Core 변경은 개인 시험 브랜치에만 있습니다.

### 3-4. 결과를 쉽게 읽으면

- **지금 Ghost-ALICE(BASE)는 비용만 늘고 검증은 거의 하지 않았습니다.**
  - 비용은 OFF의 2.5배, 시간은 6.5배였습니다. 정답률은 둘 다 100%로 같았습니다.
  - 근거 검토는 12번 중 1번 실행됐고, 검토받은 답이 그대로 전달된 경우는 0번입니다.
  - 차단 20번 중 17번이 "경로 미등록"이라는 형식 문제였습니다. 한 턴에 1번뿐인 차단을 형식 문제에 써 버려서, 정작 검토는 알림만 남기고 넘어갔습니다.
- **기록 정리를 Core가 자동으로 하자 비용이 29% 줄었습니다 (IMP).** 하지만 모델이 목적을 "실행"이라고 적으면 검토를 건너뛸 수 있었습니다.
- **검토를 확실히 하게 하자 검토 절차 자체가 비쌌습니다 (IMP2).** 12번 모두 검토했지만 비용이 BASE보다 9% 많아졌습니다. 검토 한 번에 다음 단계가 모두 들어가서 답 하나에 약 $0.27이 더 들었습니다.
  - 스킬 읽기
  - 참고 문서 찾기와 읽기
  - 파일 4개 쓰기
  - 명령 2번
- **검토를 명령 한 번으로 줄이자 검증과 비용 절감을 함께 얻었습니다 (IMP3b).** BASE보다 38% 싸고 57% 빠르면서, 근거 케이스 12번을 모두 검토했고 검토받은 그대로 전달했습니다.

### 3-5. 추가 측정: JY 방식(PR #15)과 PR #13, 그리고 함정 케이스

JY의 PR #15도 같은 문제("읽기만 했는데 Stop 훅이 경로 미등록으로 막음")를 다른 방식으로 고칩니다. 읽기 도구만 쓴 입력은 막지 않고, 검토도 하지 않습니다. 두 방식을 같은 기준선에 올렸습니다. 기준선은 Core `c6019ac` + 시험 전용 입력 확정 패치이고, 같은 케이스 6개를 번갈아 각 18회 측정했습니다. PR #13은 CI 수정과 Autopilot 보호를 포함한 최신판입니다.

| 실행당 평균 시간 | 149초 | **41초** | 46초 |
| 정답 | 18/18 | 18/18 | 18/18 |

- 읽고 알려 주는 케이스는 JY 방식이 쌉니다. PR #13의 검토 비용은 근거 케이스 기준으로 답 하나에 약 $0.12입니다.
- 파일을 만드는 케이스(K5)는 PR #13이 절반 가격입니다. JY 방식에서는 파일을 바꾼 턴이 여전히 막혀 Claude가 경로를 직접 등록했습니다.
- JY 방식의 읽기 전용 판별기는 PowerShell 읽기 명령(`[IO.File]::ReadAllBytes` 등)을 작업으로 봐서, K2 3회 중 2회를 막았습니다. 안전한 쪽의 오판입니다.
- **PR #13 최신판은 측정판(IMP3b)보다 15% 비쌉니다.** 원래 규칙 문장을 되돌린 몫과 회차 간 흔들림이 섞여 있어, PR #13의 효과는 BASE 대비 -28%로 봅니다.

**검토가 실제로 오류를 잡는지 확인한 함정 케이스.** 검토의 가치를 재려고 틀리기 쉬운 함정 케이스 10개를 만들었습니다. 정답은 미리 코드로 계산했고, 자료는 [evidence/2026-11-24/testbed2/](evidence/2026-11-24/testbed2/)에 있습니다.

- 쉬운 함정 7개: 비슷한 파일 이름, 문서와 다른 코드, 오래된 주석, 세기 함정, 긴 파일 깊은 곳, 미국식 날짜, 없는 것 묻기
- 어려운 함정 3개: 지저분한 CSV 합계, 시간대 변환, 조건부 세기

| 실행 | 횟수 | 정답 |

검토가 없어도 오류가 나지 않아 검토가 잡을 오류가 없었습니다. Opus에서는 이런 읽기·계산 작업에서 검토가 정확도를 바꾼다는 근거를 얻기 어렵다고 보고 측정을 중단했습니다(50회 계획 중 12회, 함정 측정 비용 $7.89).

| 4 | 검토를 통과한 뒤 모델이 답을 다른 말로 고쳐 내면 검토받지 않은 답이 전달됨 | IMP3에서 12번 중 5번 | "검토 실행 횟수"만으로는 보이지 않는 검증 구멍 | 시험 브랜치에서 수정 (IMP3b: 검토받은 원문을 그대로 출력해 그대로 전달). 집계에 "그대로 전달" 지표 추가 |
| 5 | 검토 근거를 모델이 손으로 베껴 씀 | BASE·IMP2 검토 기록 | 근거가 실제 도구 결과와 같은지 아무도 확인하지 않음 | 시험 브랜치에서 수정 (Core가 도구 결과를 직접 저장하고 근거 문구가 글자 그대로 있는지 확인. IMP3b에서 26번 중 8번 거절 뒤 원문으로 다시 내서 통과) |
| 6 | 측정한 세션과 시험에서는 Autopilot이 한 번도 기록하지 않음. 고장이 아니라, 기록 조건(사용자가 밝힌 완료 조건 + 그 조건을 묶은 실행 작업 단위가 든 응답 경로 + 완료 보고)을 갖춘 입력이 없었기 때문 | 분석한 세션과 BASE·IMP2·IMP3b 모든 실행에서 건너뜀 이유가 `completion-body-invalid`(Core가 답을 막는 중), `no-current-execution`(경로에 실행 작업 단위 없음), `response-no-publication`(완료 보고 없음). 경로는 모두 작업 단위가 0개였음. 반면 실제 설치본 원장에는 완료 조건을 밝힌 11/12 세션 2개에서 기록·적용 4건이 있음(조건 P1·P2, AC1~AC4를 충족으로 표시) | 완료 조건 없이 하는 일반 작업에서는 켜져 있어도 하는 일이 없음 | 원인 확인 완료. 자동 경로 등록을 쓰는 안(PR #13)은 완료 조건이 있는 세션을 제외해야 Autopilot 동작이 유지됨. 채택한 JY 방식은 경로를 대신 등록하지 않아 Autopilot에 영향 없음 |

## 5. 확인하지 못한 것

- **긴 실제 작업**: 시험은 짧은 작업 6종입니다. 긴 작업에서는 고정 비용 비중이 작아서 절감률이 38%보다 낮을 수 있습니다. 실제 세션 분석에서 관리 비용은 약 29%였습니다.
- **케이스별 차이의 확정**: 조건마다 3회라서 케이스 하나하나의 차이는 확정하기 어렵습니다. 케이스별 합격 기준(차이가 BASE 3회 흔들림보다 큼)을 넘은 것은 K2·K4·K6이고, K1·K3·K5는 평균은 낮지만 흔들림 범위 안입니다.
- **검토의 가치**: Opus로 한 함정 케이스에서는 검토 없이도 오류가 나지 않아, 검토가 오류를 잡는지 확인하지 못했습니다. 약한 모델(Sonnet, Haiku), 긴 실제 작업, 모호한 요청에서는 결과가 다를 수 있습니다.
- **판단의 정확성**: 검토는 여전히 모델이 스스로 판정합니다. Core는 근거가 실제로 있는지와 기록이 맞는지는 확인하지만, 판단이 옳은지는 확인하지 않습니다. BASE도 같습니다.
- **시험 환경과 실제 사용의 차이**:
  - 시험은 입력 확정 패치를 넣은 자동 실행이었습니다.
  - 시험용 설치에는 `PostToolUseFailure:io-trace` 훅이 없습니다.
  - 사람이 데스크톱 앱에서 쓰는 실제 사용에서는 JY 방식과 PR #13을 돌려 보지 않았습니다(JY 방식은 JY의 실사용 시험 19개 사례 × 5회가 있음, #11 보고서).
- **다른 환경**: Codex, Linux, 다른 팀원 PC에서는 측정하지 않았습니다.
- **Autopilot**: 완료 조건을 밝힌 작업에서 Autopilot이 비용 대비 얼마나 도움이 되는지는 재지 않았습니다. 이번 케이스에는 그런 작업이 없었습니다(K5도 완료 조건은 있지만 실행 작업 단위로 등록되지 않음).

  - **`core/main` 에 합쳤습니다 (11/24, `450e4b3`).** JY가 대상 브랜치를 `core/main` 으로 바꿨고, 읽기 전용 판별기가 일부 쓰기 명령(`FOO=1 rm -rf build`, `$r = Remove-Item x`, `sort -o`, `sed -n w`)을 읽기로 보던 문제도 고쳤습니다(`b03f6dc`, 테스트 추가). kyu가 쓰기 명령 13개, 읽기 명령 7개로 직접 확인했고, CI는 모두 통과했습니다. 브랜치 안내(PR #14)도 `main` 에 합쳤습니다(`153e562`).
  - 설치는 계속 태그 `test-baseline-2026-11-16` 으로 합니다. `core/main` 은 개선판을 시험할 때만 별도 폴더에 설치합니다.
