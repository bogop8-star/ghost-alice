# Windows 검증 발견 사항 (2026-11-18)

- 기준: `test-baseline-2026-11-16` (Core `c6019ac`, Autopilot `v0.5.1` `2075768`)
- 환경: Windows 11 Pro 10.0.26200, 한국어 로캘(cp949), Python 3.14 (pytest 9.2.0), Git for Windows
- 작업 브랜치: `windows-verify` (개발 worktree `C:\Users\N-\ghost-alice-autopilot-win`)

이 문서는 Autopilot 테스트를 Windows에서 실행하면서 확인한 문제를 팀에 공유하기 위해 정리했습니다. 각 항목에 실제로 확인한 범위와 확인하지 못한 범위를 구분해 적었습니다.

## 1. 테스트 결과 요약

| 실행 | 통과 | 실패 | 건너뜀 | xfail | 소요 |
|---|---|---|---|---|---|
| 수정 전 (PowerShell 5) | 740 | 22 | 2 | 0 | 47분 |
| 수정 후 (PowerShell 5) | 759 | 0 | 4 | 1 | 43분 |
| 수정 후 (PowerShell 7.7.0) | 759 | 0 | 4 | 1 | 46분 |

실패 22건 중 21건은 테스트가 POSIX 동작을 가정해서 생긴 실패였고, 테스트 쪽 수정으로 해결했습니다. 1건은 어댑터의 실제 Windows 동작 차이이며, 어댑터를 바꾸지 않고 Windows에서 xfail로 표시했습니다. 건너뜀 4건 중 2건은 원래 테스트에 있던 것이고, 2건은 Windows에서 `chmod(0o555)`로 폴더 쓰기를 막을 수 없어 추가한 것입니다.

팀원 JY도 다른 Windows PC(Windows 11 Pro, Python 3.14.4, PowerShell 7.6.10)에서 같은 브랜치를 실행해 758개 통과를 확인했고, 2.1의 xfail도 같은 방식으로 재현했습니다. 이 실행에서 생긴 실패 1건은 2.5에 적었습니다.

## 2. 실제 동작 차이 (코드 쪽)

### 2.1 실행 폴더 자리에 파일이 있으면 Windows에서는 경고 없이 넘어감 (Autopilot 어댑터)

- 증상: `GHOST_ALICE_AUTOPILOT_RUN_DIR` 가 폴더가 아니라 일반 파일을 가리키면, Stop 훅이 POSIX에서는 복구 안내(`recovery: parked`)를 내지만 Windows에서는 `recording-unavailable / authority-missing` 만 내고 안내 없이 끝납니다.
- 원인: 일반 파일 아래 경로를 읽을 때 POSIX는 `NotADirectoryError` 를, Windows는 `FileNotFoundError` 를 냅니다. 어댑터는 "파일 없음"을 "실행 기록 없음"으로 처리합니다.
- 근거: Windows에서 직접 확인했습니다. 일반 파일 아래 경로 읽기는 `FileNotFoundError` (errno 2), `os.listdir` 은 `NotADirectoryError` (WinError 267)입니다. 테스트 `test_completion_behavior_repair.py::ContinuationRecoveryTest::test_real_adapter_error_preserves_original_goal_and_answer`.
- 영향: 설정 오류가 사용자에게 보이지 않습니다. 데이터 손상은 확인되지 않았습니다.
- 처리: 기록만 합니다. 어댑터를 고치면 설치본 지문이 바뀌어 재설치가 필요합니다.

### 2.2 CRLF가 들어간 완료 문구는 기록이 거부될 수 있음 (Autopilot 완료 기록)

- 증상: `autopilot_completion.py publish` 는 완료 문구를 바이트 그대로 읽어(`sys.stdin.buffer.read()`, `Path.read_bytes()`) 검토 기록과 비교합니다. 문구 안의 줄바꿈이 CRLF이면 "Final block must match exactly one recorded assistant review" 로 거부됩니다.
- 근거: 테스트가 텍스트 모드로 입력을 넘길 때 Windows가 LF를 CRLF로 바꿔 5건이 실패했고, LF 그대로 넘기면 통과했습니다. 끝 줄바꿈만 CRLF인 경우는 통과했습니다.
- 셸별 관찰: Git Bash는 바이트를 그대로 넘깁니다. PowerShell 5와 7은 문구 안의 LF를 유지하고 끝에만 CRLF를 붙입니다. CMD는 확인하지 못했습니다.
- 영향: Claude Code는 Windows에서 Git Bash로 명령을 실행하므로 평소에는 문제가 없습니다. Windows 편집기로 저장한 CRLF 파일을 `--completion-file` 로 넘기는 경우는 거부될 것으로 추정하며, 직접 재현하지는 않았습니다.
- 처리: 기록만 합니다.

### 2.3 한국어 Windows에서 Core 완료 검토 도구가 한국어 파일을 읽지 못함 (Core)

- 증상: `completion_assessment.py prepare-response` 가 한국어가 들어간 답변 파일에서 `'cp949' codec can't decode byte 0xa4` 로 `status: unavailable` 을 반환했습니다.
- 원인: 파일을 읽을 때 인코딩을 지정하지 않아 Windows 기본 코드 페이지(cp949)를 씁니다. 팀 기준 Core(`c6019ac`)의 `_shared/completion_assessment.py` 845, 848, 851줄이 `Path(...).read_text()` 를 인코딩 없이 호출합니다. AidALL 최신 main(`7c78c69`)에서도 871, 874, 877줄에 같은 코드가 남아 있습니다.
- 우회: `PYTHONUTF8=1` 을 설정하면 정상 동작했습니다.
- 영향: 수동으로 응답 검토를 기록할 때 실패합니다. 훅 실행 경로에서도 같은 문제가 생기는지는 확인하지 않았습니다.
- 처리: Core는 이번 범위가 아니므로 기록만 합니다.

### 2.4 Windows 테스트 실행기가 PowerShell 5에서 바로 멈춤 (이번 브랜치에서 수정)

- 증상: 기본 파이썬에 pytest가 없으면 `run_windows_tests.ps1` 이 설치 단계로 가지 못하고 `NativeCommandError` 로 멈췄습니다.
- 원인: PowerShell 5에서 `$ErrorActionPreference='Stop'` 이면 외부 프로그램의 stderr 출력이 종료 오류가 됩니다. 또 PowerShell 5는 외부 프로그램 인자 안의 큰따옴표를 지웁니다.
- 수정: 파이썬 버전과 pytest 설치 여부를 stderr를 쓰지 않는 한 번의 확인으로 검사하고, 없으면 무엇이 없는지 알려 주고 멈춥니다. 패키지를 자동 설치하지 않습니다. PowerShell 5와 7에서 pytest 없는 파이썬, 없는 경로, 정상 파이썬 세 경우를 확인했습니다.

### 2.5 병렬 상태 갱신 테스트가 Windows에서 가끔 실패함 (관찰만)

- 증상: JY PC의 전체 실행에서 `tests/test_autopilot_state.py::AutopilotStateTest::test_parallel_advance_claims_ready_item_once` 가 `PermissionError` 로 1번 실패했습니다.
- 재실행: 같은 테스트만 5번 다시 실행했을 때는 5번 모두 통과했습니다. kyu PC의 세 셸 전체 실행에서는 실패하지 않았습니다.
- 원인(추정): 여러 프로세스가 같은 파일에 동시에 접근할 때, Windows는 다른 프로세스가 연 파일을 바꾸거나 지우는 것을 POSIX보다 엄격하게 막습니다. 코드는 아직 확인하지 않았습니다.
- 처리: 기록만 합니다. 다시 실패하면 그때 원인을 조사합니다.

## 3. 테스트 쪽 차이 (수정 완료)

| 원인 | 건수 | 수정 |
|---|---|---|
| Windows `chmod(0)` 은 파일 읽기를 막지 못함 | 8 | `deny_read` 함수: Windows에서는 `icacls` 로 현재 사용자 SID의 파일 내용 읽기(`RD`)를 거부하고, 읽기가 실제로 막혔는지 확인한 뒤 막히지 않는 계정이면 사유를 적고 건너뜀 |
| 텍스트 모드 입력의 LF→CRLF 변환 | 4 | `run_exact_stdin` 함수: 완료 문구를 UTF-8 바이트 그대로 전달 |
| `shlex.join` 이 Windows 경로를 따옴표로 감싸 문자열 비교 실패 | 3 | `is_publish_command` 함수: 명령을 인자 단위로 나눠 비교 |
| `chmod(0o555)` 로 폴더 쓰기를 막을 수 없음 | 2 | Windows에서 사유를 적고 건너뜀 |
| `'/Library'` 가 Windows에서 절대경로가 아님 | 2 | `os.path.abspath(os.sep + 'Library')` 사용 |
| 오류 문구가 한국어(`WinError 183`) | 1 | Windows에서는 `WinError 183` 확인 |
| 자식 프로세스에 `USERPROFILE` 이 없어 홈 폴더를 못 찾음 | 1 | 설치 스크립트 실행 시 `USERPROFILE` 전달 |

모든 수정은 POSIX 동작을 바꾸지 않도록 Windows 분기 또는 양쪽에서 같은 결과를 내는 방식으로 했습니다. GitHub CI(Linux)에서 762개가 통과해, Windows에서 건너뛰거나 xfail로 둔 테스트도 Linux에서는 그대로 통과함을 확인했습니다.

## 3-1. 셸별 격리 설치 확인

PowerShell 5.1, PowerShell 7.7.0, Command Prompt에서 각각 Core `_shared/install_hooks.py` 를 격리 위치(`--destination-file`, `mode: isolated`)로 실행했습니다. 세 셸 모두 install, `--status`, `--uninstall` 이 종료 코드 0으로 끝났고 오류·경고 출력이 없었습니다. install은 Autopilot 훅 2개(`prepare-origin`, `continue`)를 등록했고, status는 installed를 보고했고, uninstall은 훅 8개를 모두 지웠습니다. 실행 전후 실제 사용자 설치 파일 921개와 설치 폴더 두 곳의 상태가 같았습니다. 이 근거로 호환표 Windows 항목 3개를 `verified-local` 로 올렸습니다.

## 4. Ghost-ALICE 규칙 누락 관찰 (이 작업 세션)

이 작업을 진행한 Claude Code 세션(`95c6673a`)에서 Stop 훅의 완료 점검이 다음 경고를 냈습니다. 모두 Claude가 Ghost-ALICE 규칙을 빠뜨린 사례이며, 경고 후 기록을 보완해 통과했습니다.

| 경고 | 횟수 | 빠뜨린 규칙 |
|---|---|---|
| `route-unavailable` | 2 | 도구를 쓰기 전에 응답 경로(response-route)를 등록하지 않음 |
| `criterion-unbound` | 5 | 근거를 바탕으로 한 설명 답변에 응답 검토(response review)를 기록하지 않음 |

응답 검토 기록 과정에서 2.3의 cp949 문제도 함께 발견했습니다. 이후에는 답변 전에 경로 등록과 응답 검토를 먼저 하도록 바꿔 경고가 줄었습니다.
